# 给NSFW维护者：手机图片审核与提示词评分接口需求 v2

2026-10-28；请求方MediaReview。本文是接口提案，不表示接口已经实现或获准部署。仅在MediaReview仓库记录需求，不修改NSFW工程。

## 目标及接入边界

手机新增与“批阅”同级的“生图审核”页面。持续生成的新图片追加到队尾，不打断当前浏览；每图可查看生成时的提示词、生成时间、尺寸等；手机评分复用桌面已有提示词人工评分体系。

**不申请新端口**：复用8767 Mobile Review Bridge及现有Bearer配对。8000保持loopback，不向手机开放完整prompts/jobs/engine管理路由，不直连ComfyUI。新增能力使用审核桥的受限DTO和明确能力标记；原手机合同继续兼容。

已读基线：NSFW双目录6ad633a，桌面评分服务prompt_scoring_service、prompts路由、PromptEvaluation模型及PromptScoringDialog；实施前维护者应确认自己的最新版本。

## A. 必需：持续发现图片

建议新增`GET /mobile/images/feed?cursor=...&limit=50`，首次无cursor，返回按服务端稳定顺序排列的items、next_cursor、has_more。路径可由维护者调整，但须冻结合同和fixtures。

- image_id为稳定身份；排序由服务端游标/序列决定，不依赖手机时间，不单用created_at作为唯一游标。必须覆盖相同时间多图、跨页边界、并发提交、延迟入库。
- 首次获取可设定明确起始范围，说明是否包含全部历史；分页追平后保留游标，下一轮仅取新增/变更。空增量不代表旧图被删除。
- 明确create/update/remove事件语义、事件唯一ID或可去重版本、游标过期状态码和恢复方法。断线重放不产生重复卡片。
- 图片摘要至少包含现有MobileImageSummary字段、生成时间语义及可用的提示词身份信息；图片内容仍用现有thumbnail/preview/original接口和同源相对URL。
- 手机已有队列顺序保持，新发现图只追加；同ID元数据更新原位刷新，不插到当前图片之前。大量历史数据必须分页，不返回整库。

当前冻结sessions不能发现后来生成的图，不能让手机不断新建session来冒充增量发现，这会改变全局latest并干扰恢复。

## B. 必需：图片详情及提示词归属

建议`GET /mobile/images/{image_id}/details`提供：

| 字段 | 要求 |
| --- | --- |
| image_id | 与feed、图片二进制和审核使用同一身份 |
| generated_at / created_at | 明确是生成完成还是入库时间，统一带时区；不能将手机接收时间当生成时间 |
| width / height | 原图尺寸；未知允许null并明确口径 |
| positive_prompt / negative_prompt | 生成时保存的快照，未知为null，实际空字符串和未知不能混淆 |
| prompt_id / prompt_version_id | 服务端权威关联，附关联状态：exact / unresolved / unlinked等明确枚举 |
| job_id / module_id / seed | 可空，有则展示 |
| model / size_bytes / mime | 可选常规信息；无则不伪造 |
| updated_at / revision | 供详情/审核并发核对及缓存更新使用 |

提示词被编辑后，旧图仍须展示旧生成快照。禁止用当前Prompt正文替换历史快照，禁止手机按文本相同就自动认定同一个prompt_id或版本。没有可靠关联时允许看图及快照，禁用“写回提示词评分”，说明原因；不擅自创建或合并提示词。

## C. 必需：动态图片的审核写入

现有decision定位冻结session内条目；后来发现的新图不在旧session中。维护者需选择并冻结一种方式：

1. 推荐按image_id提交受限审核动作，沿用KEEP/REJECT/RESET/favorite与expected_updated_at；或
2. 由服务端安全追加到原session尾部，并提供增量队列、全局index、total/seen/complete一致性规则。

不能让手机猜测任意image_id能在旧session中提交。两种方案都要求：认证、原子状态变更、409冲突、结果未确认时可查权威状态；REJECT只改状态，不删除文件。能力未具备前手机不虚报审核成功。

## D. 必需：提示词评分读写（复用现有体系）

现有桌面事实：总分1–5分；7个可选维度subject/clothing/scene/composition/lighting/style/quality（人物/服饰/场景/构图/光影/风格/画质），每维1–5分；notes；prompt_version_id可空。每次保存新增PromptEvaluation历史记录，评分本身不会改变提示词keep/candidate/eliminated状态。

建议桥提供以下受限能力（提议路径，待维护者冻结）：

- `GET /mobile/prompts/{prompt_id}/review-summary?version_id=...`：返回明确评分目标、该版本最新评分、可选提示词整体最近评分（必须标出所属版本）、历史条数和图组样本统计。
- `GET /mobile/prompts/{prompt_id}/images?version_id=...&cursor=...&limit=...`：仅该提示词版本关联图片的有界列表，包含当前图的定位信息；可按job分组观察不同批次，不开放任务管理。
- `POST /mobile/prompts/{prompt_id}/evaluations`：复用现有评分DTO和校验，带准确prompt_version_id、总分、用户实际填写的维度和notes；返回evaluation_id、服务端时间和权威评分。允许仅总分，未评维度省略，不默认填3分。

手机不写数据库、不复刻桌面评分服务。桥可内部调用现有评分服务，不能把整个桌面Prompt编辑/淘汰功能直接暴露出来。

**版本口径**：建议手机评分对象固定为prompt_id + 生成时的prompt_version_id。同一提示词不同版本分开呈现；桌面目前latest_evaluations按prompt_id聚合最新一条、跨版本，不能把该结果不加标识地展示成某个版本的分数。请维护者提供精确版本评分查询，并说明桌面如何显示带版本的手机评分。不能绑定版本时不得默认绑定当前最新版。

兼容历史图片：如果prompt_id可靠、只有生成版本缺失，可让用户明确选择“对提示词整体评分（生成版本未知）”，写prompt_version_id=null，和版本评分分开展示；不能无提示地替用户选择这个范围。如果连prompt_id也不可靠，则仅展示快照，不允许猜测写回对象。

**追加历史与防重复**：桌面当前保存为新增历史记录，不是覆盖同一行。手机重新评分也沿用新增一条；提供client_request_id/幂等键及查询回执，网络重试不应产生多条相同评分。如果暂不支持幂等，手机只能“提交一次→超时标为未确认→查询历史核对”，不能盲目自动重发。并发评分明确采用历史追加及最新规则，保留来源/设备/评分时间，不静默删除桌面评分。

## E. 推荐的手机评分交互

图片审核按单图进行，提示词评分按版本图组进行。每张图都能点“提示词评分”，进入同一版本的共享面板，而不是给每张图复制一份提示词分数。

面板先显示本提示词版本的多张缩略图（当前图标记）、已看/关联总数、KEEP/REJECT计数，再显示总分1–5及可展开的7维评分、备注、已有评分时间。初期直接显示常规字段，不为视觉探索延迟核心接入。

示例：同一提示词v3有12张图，已看8张，保留6、驳回2。用户结合这8张给v3评4分；剩下4张或后来新生成图出现时，仍显示“已有4分，评分后有新样本”，可自愿复评。**不因为新图到来清空或自动改分。** “评分时看了几张”只有明确提供可记录的证据字段后才作为权威历史信息；否则仅显示当前浏览计数，不伪造追溯证据。

不把KEEP比例自动换算为提示词总分，不把单图分数简单平均成提示词评分。同一提示词的效果还受模型、参数和seed影响，图组可按job/module辅助查看，备注记录具体批次；首期不建立另一套模型评分或自动评分体系。

建议至少观察若干张不同seed样本再打分，但不设必须审完全部才能评分的硬门槛；持续生图意味着图组可能永远不会“全部完成”。只审图片不等于已经评过提示词；打低分也不自动驳回所有图片或淘汰提示词。

## F. 最小验收及回交材料

1. 同时生成多图和跨页持续入库，手机不漏图/重复图，停留位置不跳；断线恢复能追增量。
2. 图片元数据的正/负提示词为生成快照，旧版本不误绑定到新版本；unlinked图片仍能正常查看。
3. 同版本多图共享一个评分目标，手机保存后桌面能读到对应历史记录；已有桌面评分回到手机可见。
4. 总分1–5、维度白名单、仅总分、null版本的限制、旧版本、401/409、保存成功但响应丢失均有针对性用例。
5. 提供更新的OpenAPI/字段说明、能力标记、错误码、合成fixtures和调用示例，注明版本/commit；不提供凭据或生产数据。

MediaReview负责独立一级界面、图片浏览/信息、稳定队尾追加、配对凭据隔离、评分展示与回传、模拟器回归；NSFW维护者负责桥接口和上游语义。NSFW未修改，新增端口需求为零。
