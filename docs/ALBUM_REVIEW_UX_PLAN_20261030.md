# 相册与生图审核体验修复计划

基线：Alpha25/code32，`97ec56b`。用户明确要求媒体库一键全选、相册按可见范围加载、生图图片占比更大。本轮按此交互实施，复用既有页面、分页、缓存与配对。

1. 媒体库：`LibraryManagerViewModel`增加全选/清空草稿，`LibraryManagerScreen`固定显示选择数量与批量按钮；仍仅“应用”提交，保存时禁止改草稿，空选仍拦截。复用该ViewModel测试，补批量选择回归。
2. 相册：`ShelfGrid`持有实际滚动状态，预取当前附近最多8个封面；删除`HomeScreen`在视频页也预取相册的重复任务；统一封面解码尺寸，滚动/离页取消过期预取。照片页仍50条分页、只加载可见卡片及附近预取，保留既有相册自选封面与身份。书架首载明确显示加载，刷新依据真实请求状态、保留旧内容。目录树和书架独立加载，不让目录树阻塞相册。复用WindowCachePolicy及相册分页测试。
3. 生图：去掉压在图片上的信息层，元数据放“图片信息”；缩略图默认折叠，保留/淘汰合并为紧凑主操作行，其他操作与翻页紧凑排列，保留撤销及新图提示。图片独占余下空间、Fit完整显示；提交需当前预览成功并保留原写入/revision守卫。顺手修正同屏评分1–5自适应宽度，避免5分被裁切。无真实评分/审核写入。
4. 验证与交付：单worker串行运行改动相关JVM，必要编译，一次签名Release构建Alpha26/code33。核验版本/签名/哈希，手机保留数据覆盖后定向检查全选草稿、相册加载与滚动、图片区域和1–5布局；手机不可用如实记录。更新状态、日志、唯一APK指针，commit/push。生产服务、NSFW源码、数据库迁移、真实媒体不动。

现有证据：本机日志相册请求50/143约5964ms，文件夹聚合约4.4–5.2秒；不承诺只改手机就消除服务端查询耗时。若仍需服务端专项，独立定位和交付，不能把预取有界等同于全链路性能验收。
