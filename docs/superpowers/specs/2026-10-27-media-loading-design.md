# 图片与视频加载专项方案（待确认）

## 目标与边界

以Alpha17和Server1.6.1源码为基线，改善图片墙、图片查看、视频首播与批阅切换。用户确认雪碧图已主动砍掉，保持删除；不改UI结构、批阅/删除流程，不换播放器，不部署额外服务，不操作真实媒体。生产升级仍独立授权。这里是可审阅的实施范围，尚未改生产代码。

## 方案选择

| 方案 | 收益与代价 |
| --- | --- |
| A：分段优化现有链路（推荐） | 先图片缓存/调度、Server图片I/O、首播分段计时，再按证据缩短串行请求，最后验证有界视频内容预缓冲；可逐段回退，资源占用可控。 |
| B：仅增大并发、缓冲和缓存 | 改动少，但可能加剧磁盘/上游竞争，不能保证解决可见项等待，不采用。 |
| C：替换播放器或媒体服务 | 能重做预加载架构，迁移和验收范围大，本专项不采用。 |

## A方案的数据流与改动

### 1. 图片

共用现有Coil ImageLoader与认证隔离机制。列表显示、相册/目录封面、预取和查看器占位共用可兼容的缓存键：服务/账号命名空间、资源身份或版本、尺寸档位；重试仍能重新请求，退出配对/切服务不串图。不对已有正确的原图缓存校验作全局放宽。

移除先等固定首批预取完成再监听滚动的顺序依赖；当前可见区域优先，方向改变取消旧预取，预取继续有界且不抢当前原图。图片详情先复用现有小图，再显示当前大图，相邻原图在当前成功后才低优先预取。本轮先不新建中尺寸图片API，以下载字节及首图基准判断是否值得后续增加。

Server缩略图缓存读写移出事件循环，保留同键请求合并、异常传播及缓存失效。负缓存如确有重复缺图证据，仅用于明确404，短TTL、数量有界；401/403和暂时5xx不能冒充缺图。取消请求不得留下不完整文件。

主要位置：`WindowLoading.kt`、`MediaComponents.kt`、现有封面组件、`ZoomableImage.kt`/图片请求辅助层、`thumbnail_cache.py`及相关已有测试。按实际调用收敛修改文件，不做全仓格式化。

### 2. 视频

先补齐/复用分段指标：播放信息获取、上游解析、播放器准备、实际首帧。仅记录脱敏标识与耗时，不记录带凭据URL或真实路径。地址已返回、时间轴前进均不算首帧。

以隔离上游受控延迟验证 `/playback` 的串行等待。仅在必要信息与错误语义可保持时并行独立读取或延后可选信息；不跳过设备凭据、地址安全检查，不代理Jellyfin视频，不移除HLS回退/续播行为。

随后用现有GSY/Media3做小范围接入验证：当前视频稳定后，仅下一条可预缓冲少量内容，缓存总量有上限，快速切换取消，保留认证头、媒体身份和回退。必须证明播放器复用了预取数据，且当前播放不退化；不使用独立下载器盲目下载固定文件头，也不假设简单打开 `cacheWithPlay` 即完成。若GSY无法安全共享数据源，停止该子项，交付前两段已验证收益与具体限制；不扩成播放器重写。

主要位置：`V2ReviewViewModel.kt`、`V2PlaybackSourceController.kt`、现有GSY控制层、`media.py`及对应测试。预缓冲实现前核对Media3 1.10.1/GSY 13.2.1实际API。

## 验证与交付

先用同一批可丢弃合成图片/视频与受控延迟取得冷/热缓存、快速滚动、连续切换基准。改动后对照请求量、下载量、缓存命中、首图/首帧耗时、取消后浪费量；数字只代表实际执行的场景。真实Wi-Fi和手机硬件解码由用户回家后复核。

每段只运行直接相关Server pytest或Android JVM测试，必要编译，串行运行。缓存隔离、取消传播、错误归类与鉴权边界不能省；不重跑无关全量/178项connected。已有模拟器Surface异常须单独记录，不能宣称视频出帧通过。没有测出收益的调参不作为提速交付。

交付：专项简报、定向测试/前后对照结果、Git提交与push实况；Android变更经必要验证后提供升级APK，Server变更提供对应部署包。生产升级、邮件发送另按实际授权执行。本专项结束后停止，不自动新增媒体架构阶段。
